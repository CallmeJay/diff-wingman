# Diff Wingman 开发路线图

本文记录 `v0.0.5` 之后的产品方向和拟议版本范围。路线图用于约束后续讨论与开发，不代表其中所有功能已经实现；每个版本开始开发前，仍需单独确认范围、交互和数据契约。

## 产品目标

Diff Wingman 首先是一款帮助人工理解和核对代码变更的本地 diff review 工具。后续功能优先服务三个目标：

1. reviewer 能快速找到并读完每一处真实变更；
2. reviewer 能明确知道哪些内容已看、哪些有疑问、哪些需要重新审查；
3. 每条 AI 解释和人工结论都能回到固定版本的源码证据，不用模型输出代替人工审查。

平台写入、自动修复、自动批准和团队协作不能挤占基础 diff review 的开发优先级。

## 当前基线：v0.0.5

当前版本已经具备：

- 本地 commit、暂存区和工作区比较；
- GitLab MR 固定版本只读导入；
- 变更文件列表视图和树形视图；
- 并排、内联、空白变更显示和单文件显示模式；
- Codex 阅读路线、需求对照、流程步骤和源码引用；
- 分组、逐条判断、人工依据和本地笔记；
- GitLab 单行评论草稿及 Markdown 导出；
- 快照新鲜度检查和 Docker 隔离验证。

## v0.0.6：Review Core

这一版只补齐日常 diff 阅读和进度管理，不增加新的代码托管平台。

### 1. 按变更块阅读

- 默认保留有限上下文并折叠大段未修改代码；
- 显示每个 hunk 的原始范围；
- 支持向上、向下扩展固定行数以及展开完整文件；
- 支持跳转到上一个或下一个变更块；
- 长文件滚动时保持文件标题和操作入口可见。

### 2. 文件级审查状态

每个文件提供以下人工状态：

- 未阅读；
- 审查中；
- 有疑问；
- 已审查。

状态必须绑定当前文件内容和 diff 身份。默认只允许 reviewer 主动标记“已审查”，不能因为文件被打开或滚动到底部就自动完成。源码发生变化后，旧状态保留为历史记录，但不得继续显示为当前版本已审查。

页面需要显示已审查、有疑问和未审查的文件数量，并提供“下一个未审查文件”。

### 3. 文件搜索与筛选

- 按文件名和完整路径进行模糊搜索；
- 按新增、修改、删除和重命名筛选；
- 按人工审查状态筛选；
- 按源码、测试、配置、样式、文档和锁文件筛选；
- 按有评论、待确认和无法分析筛选；
- 列表视图与树形视图共享同一组搜索和筛选条件。

### 4. 阅读导航

- 上一个、下一个文件；
- 上一个、下一个变更块；
- 打开文件搜索；
- 标记当前文件已审查；
- 在当前 diff 位置创建评论；
- 快捷键不能在输入框和编辑器输入状态下误触发。

### 5. 持久化与验收

- 关闭并重新打开应用后，文件状态、筛选偏好和当前阅读位置可恢复；
- 每个可分析 hunk 都能被导航到，折叠上下文不能隐藏真实变更；
- 文件状态只属于对应快照，不能跨内容变化静默继承；
- 100 个变更文件的快照中，可以只显示未审查文件并连续完成导航；
- 原有阅读路线、笔记、评论草稿和报告行为保持不变。

## v0.0.7：增量复审与评论闭环

这一版解决 MR 更新后从头复审以及评论难以集中处理的问题。

### 1. MR 版本间比较

- 支持“目标分支到最新 MR”以及“上次审查版本到最新 MR”两种范围；
- 明确展示本轮新增、再次修改、保持不变和已经移除的变更；
- 对 rebase 带来的变化和作者实际修改尽可能分别展示；无法可靠区分时必须标为待确认。

### 2. 安全继承审查记录

- 文件和 hunk 指纹完全一致时，允许保留原审查结果；
- hunk 内容变化时，只将对应 hunk 和文件标为需要复审；
- 路径移动或上下文变化但内容一致时，需要显示继承原因；
- 无法唯一匹配时，不自动迁移状态、结论或评论位置。

### 3. 评论能力

- 支持单行、多行和文件级评论草稿；
- 评论可标记为问题、阻断、建议或细节；
- 支持修改建议代码块；
- 支持未解决和已解决状态；
- 提供评论总览，并能跳回原始 diff 位置；
- MR 更新后，失效或存在歧义的锚点必须标记为待重新定位。

### 4. 验收要求

- MR 新版本只改变一个 hunk 时，其他未改变文件不会被错误标为待复审；
- 同一行附近发生重复代码移动时，不得凭文本相似度自动迁移评论；
- 评论总览和 diff 内显示使用同一份状态；
- 默认仍只保存本地草稿，不向 GitLab 写入。

## v0.0.8：逐处变更理解

这一版增强现有阅读路线，让 reviewer 能在 diff 旁理解每个 hunk，而不是只阅读整体总结。

### 1. Hunk 解释卡

每个变更块可以展示：

- 改了什么；
- 修改前的行为；
- 修改后的行为；
- 与哪条需求相关；
- 可能影响的调用方和状态；
- 失败路径及需要人工核对的内容；
- 已有测试、运行证据和仍缺少的证据。

每条判断必须标明来源属于源码直接证据、需求或 MR 描述、AI 推断还是待确认信息。点击证据必须能回到固定快照中的确切文件和行范围。

### 2. 变更覆盖矩阵

以 hunk 为最小单位汇总：

| 内容 | 说明 |
| --- | --- |
| 需求关联 | 对应需求、不得改变项或尚未关联 |
| AI 导读 | 已解释、待确认或未分析 |
| 人工状态 | 未阅读、已理解、有疑问或已核实 |
| 评论 | 评论数量及是否仍有未解决问题 |
| 验证 | 已执行的验证记录及其对应快照 |

任何没有进入阅读路线的 hunk 必须出现在“未分析”区域，不能因为其他文件已经生成导读而被隐藏。

### 3. 符号上下文与影响链

reviewer 在 diff 中选中完整的方法、常量、变量、类或类型名称后，可以按需查看该符号在固定快照中的上下文：

- 定义和类型信息；
- 谁调用或引用它；
- 它调用或引用了什么；
- 读取、赋值、参数传递、返回值和状态写入位置；
- 相关测试和本次变更块；
- 修改前、修改后新增、删除和保持不变的关系。

影响链不能只显示抽离文件来源的节点或上下文片段。关系图旁必须同时展示完整的“相关文件”清单，让 reviewer 可以从关系直接进入对应文件的 diff 或固定源码。

相关文件按用途分组：

- 当前定义文件；
- 入站调用和引用文件；
- 出站调用和依赖文件；
- 数据来源、转换和状态写入文件；
- 相关测试文件；
- 仅通过静态或文本匹配得到的候选文件。

每个文件至少显示完整路径、关系类型、命中符号或行号、本次增删行数、人工审查状态，以及该关系属于修改前、修改后还是两侧都存在。一个文件存在多种关系时合并展示关系标签，但保留每一处可点击的位置。点击文件进入该文件 diff；点击具体位置跳到对应固定快照的行；从 diff 返回时保留原来的影响链、筛选条件和展开状态。

关系图、相关文件和引用明细使用同一份节点与边数据，并保持双向联动：选中图中的节点时筛选并高亮相关文件，选中文件时高亮它参与的关系路径。任何无法定位到文件、blob OID 和行范围的关系都不能显示为精确关系。

第一阶段只支持 JavaScript、TypeScript、JSX 和 TSX，并遵守以下边界：

- 只处理可以定位到单一语义符号的完整标识符，不把任意代码片段强行解释为一个符号；
- 默认展示一层关系，允许 reviewer 手动继续展开下一层，避免大范围调用图失控；
- 每条关系标记为“精确符号引用”“静态候选”或“文本候选”；
- 分别基于修改前和修改后的固定快照计算关系，结果绑定文件 blob OID 和快照；
- AI 只总结已经提取并展示的关系，不自行补充不存在的调用边；
- 源码、索引或导读变化后，旧的人工确认状态必须标为待重核。

调用关系与数据流必须分开显示。“谁调用它／它调用谁”属于调用关系；“值从哪里读取、经过哪些转换、最终写到哪里”属于数据流。闭包、高阶函数、回调、事件总线、依赖注入、动态属性、React 状态和运行时注入无法由静态分析完全证明时，必须保留不确定性。

首期验收至少覆盖：

- 选中变更方法后，可以看到精确定义、直接调用者、直接被调用方法及相关测试；
- 选中常量后，可以看到定义、读取、写入和作为参数传递的位置；
- 同一符号修改前后关系发生变化时，可以明确看到新增和删除的边；
- 同名局部变量、重命名导入和不同文件中的同名符号不会被合并成同一精确关系；
- 动态调用和无法解析的路径进入候选或待确认区域，不显示为已经证明的调用链；
- 点击任一节点或关系可以回到对应快照中的确切文件和行范围；
- 相关文件清单覆盖关系图中的所有文件，并能按关系类型、修改前后状态和人工审查状态筛选；
- 从相关文件进入 diff 并返回后，影响链和当前审查位置不会丢失；
- 图形节点、相关文件和引用明细之间不存在无法追溯来源的孤立精确关系。

### 4. 上下文增强

- 从影响链继续跳转到定义、调用候选和相关测试；
- 显示调用关系的证据来源和覆盖边界；
- 别名路径、动态调用、运行时注入和未加载文件继续明确标为待人工核对；
- 不把静态匹配或模型解释表述为已经证明的运行时调用关系。

## 后续候选

以下能力暂不绑定具体版本，只有基础 review 闭环稳定后再安排：

- GitHub PR 只读导入；
- 经人工预览后批量发布 GitLab 评论；
- 按 commit 分组阅读；
- 图片、SVG、二进制和依赖锁文件专用 diff；
- 自定义审查清单和专项审查模板；
- 团队审查记录与多人协作；
- 应用签名、公证、自动更新和正式安装包。

## 明确不自动执行的操作

除非未来版本经过单独确认，Diff Wingman 不应自动：

- 修改被审查仓库、工作区或 Git index；
- 应用 AI 生成的修改；
- 发布评论、批准或合并 MR/PR；
- 把 AI 导读或脚本退出码当作审查通过；
- 在无法唯一对应新旧变更时迁移人工结论。

## 版本实施规则

每个版本开发前建立独立的范围与契约文档，并明确：

1. 用户可见行为及不允许改变的现有行为；
2. 数据结构、持久化和旧记录兼容方式；
3. 快照变化、空值、超限、并发和失败路径；
4. 正常、边界、失败及旧功能回归的验收证据；
5. 真实环境仍未验证的部分。

路线图变化时应直接更新本文；已经完成的功能应移入对应版本的范围和验收记录，不继续以“计划中”描述。
