## 现有契约与实现边界

- 验证对象继续来自 `verificationCases` 和当前导读；判断与 hunk 的关系复用 `listClaims` 的 `changeIds`，问题复用所属分组的 `changeIds`。只有未确认的当前 hunk 判断进入默认列表；没有匹配项时才看当前功能。切换范围和搜索不改变已选判断及表单输入。
- 验证任务继续通过原有接口按人工填写的判断 ID、脚本、触发条件、预期结果执行；无可用脚本时可以阅读判断，但不能运行检查。脚本退出码不自动完成业务判断。
- 符号选择仍要求当前 diff 中完整的 JS/TS 标识符；解析失败只显示后端错误，不伪造候选。面板中 `exact`、`static_candidate` 与 `text_candidate` 的含义和静态分析边界不变。
- GitLab 仍只从与所选仓库匹配的 MR 读取固定版本；缺少 MR 提交时由用户自行获取。表单的失败提示复用原错误文本，按已知权限、配置、远端、网络与本地提交错误给出下一步。
- 不增加持久化字段，不修改快照、导读、验证记录、符号分析或 GitLab 服务端契约。

## 验收重点

- 100 多条判断下，默认列表与当前 hunk/功能对应；全部搜索可找到目标；无匹配时有明确反馈；切换后已填字段不丢失。
- 无检查脚本时不运行；无法解析的符号有就地错误，有效符号仍能打开影响链。
- MR 缺少读取权限和本地提交时，表单附近给出不同的人工动作；被审查仓库和 MR 均不被修改。
