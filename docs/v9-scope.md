# v0.0.9 范围与契约：按功能查看改动

## 已确认的用户要求

| 用户原话 | 目标对象 | 允许变化 | 保持项 |
| --- | --- | --- | --- |
| “把按功能改动总览加进去做下一版本” | 现有 AI 阅读路线 | 根据全部固定 diff 变更和可用的 commit message 展示功能/变更主题总览 | 提交描述只是作者意图线索；业务判断仍以固定 diff 的源码证据为准 |
| “每一个功能可以点击，罗列出对应所有的文件改动” | 阅读路线导航 | 点击分组展开对应文件及其所有变更块，能逐项跳转 | 不改动原有文件列表、人工状态、评论和验证结果 |
| “一个文件里涉及多个功能改动……突出涉及当前功能的改动部分” | 文件 diff | 同一文件可列在多个功能下，按当前功能对应的 Git hunk 高亮 | 其他改动继续可读，不改变 diff 内容 |
| “A” | 混合变更块 | 同一 hunk 混有多个功能时列为待人工核对，不推断精确行归属 | 不新增逐行归属或把整个文件误标为当前功能 |

## 数据与失败边界

- 复用导读 `groups[].changeIds` 与 `unreviewed`：每个固定快照的变更 ID 恰好出现一次。文件列表和高亮范围由这些 ID 及快照行范围计算，不让 AI 输出像素或行位置。
- 导读生成时按功能或独立变更主题分组；不能可靠归属的混合 hunk 进入“未分析/待核对”。大快照仍按现有文件分批，跨批次分组可能相似，界面不得声称已自动合并为唯一功能。
- 仅两次提交或 GitLab MR 的固定提交快照可读取 `base..target` 中的 commit subject；要求 base 为 target 的祖先。暂存区、工作区及无法确认祖先关系时不用提交描述。读取量受限并明确显示截断或不可用原因。
- 旧审查记录没有提交描述时仍可阅读现有导读与人工记录；重新生成导读才会使用提交描述。功能清单由已保存导读实时计算，不新增独立持久化状态。
- 功能高亮只影响显示；点击变更沿用现有跳转和阅读位置保存。不能改变快照、评论、人工理解/审查状态或验证结论。元数据变更可列在文件清单中，但没有可高亮的文本行。

## 验收重点

- 一个功能跨多个文件：每个文件和变更块均可找到并跳转。
- 一个文件包含多个功能的不同 hunk：同一文件分别列在两项下，切换后只高亮当前项的 hunk。
- 混合 hunk 或无法读取的文件：显示待核对，不误归属或伪造行高亮。
- 删除、新增、重命名、元数据变更及并排/内联、多文件/单文件模式都保持原有阅读能力。
- 旧导读、无提交描述、提交历史非祖先关系和提交描述数量超限时仍可使用功能清单。
